What is being measured?

Each mode starts with a fresh copy of the scene, warms up for 30 frames, then measures 120 frames with one physics step per frame. The scene, timestep, iterations, canvas size and drawing quality stay the same. These controlled measurements differ from the live demo, which may run several physics steps per frame.

Worker timings are estimates and vary with browser scheduling, background activity and GPU clock speeds. Workers are generally less affected by main-thread page work, but still share the computer’s resources. Repeat runs before judging small differences. WebGPU physics and drawing use GPU timestamps when available. CPU physics uses wall-clock time around the solver step. “CPU work” includes submission and drawing preparation; CPU physics is included for the CPU backend. “Page delay” measures how late a 10 ms page timer runs. It shows whether the controls are being held up; it is not solver time.

During measurement, the page sends the same 120 pointer updates per second in every mode. Shared input keeps the latest pointer position, so old moves can be skipped. Clicks, keys and commands still use ordered messages. No GPU pose buffers are copied through shared memory.

CPU 2D drawing uses Canvas 2D and needs no WebGPU device. CPU 3D comparisons use WebGPU drawing with CPU pose uploads. Babylon comparisons use WebGPU physics and thin instances. The naval water simulation requires WebGPU and its direct water renderer.

Shared buffers require a secure context and cross-origin isolation. Ordinary worker messages work without those headers. This comparison uses one dedicated worker, not a pool of parallel physics solvers.
